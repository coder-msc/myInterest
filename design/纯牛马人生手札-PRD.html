纯牛马人生手札

工资去哪儿了、钱放在哪、去过哪、经历过什么、还有什么日子在等你 —— 一个 App 全记下。

本稿是在现有「攒息」仓库内做产品二次定位的设计方案：复用已打磨好的账号体系、三端脚手架、运营后台与定时任务，把原本只服务投资分红的骨架，改造成一个覆盖记账、旅游、家庭资产、人生大事件、重要日子倒计时的个人人生记录工具，移动端优先。

最大新增成本 媒体（照片）上传与存储 必须新建 全项目目前一张图片都不能上传。旅游和大事件两个模块全靠照片，这是第一个必须先行的地基。

1产品契约 用户、任务、触发、完成条件、共同对象

1.1 主要用户

25–40 岁的城市打工人，自嘲为「牛马」。有记录意愿但没记录习惯：账记三天就断、旅游照片烂在相册、家庭资产散在 Excel 和几个券商 App 里、纪念日只靠手机日历的默认提醒。

他们的共同点是不想要一个专业工具，想要一个「随手扔进去就行」的容器。所以本产品的成败标准是录入摩擦，不是分析深度。

1.2 核心任务与触发时机

模块用户要完成的事触发时机
账本记下一笔收支，并且月底知道钱花哪了付款后 5 分钟内；或睡前一次性补记
日子不忘记重要的日子，并提前有心理准备知道某个日子时一次性设定；之后靠提醒被动触发
家庭资产知道「我家到底有多少钱」低频：季度盘点，或发生大额变动时
足迹 · 旅游一趟行程结束后，留下可回看的记录行程进行中随手拍；结束后整理
足迹 · 大事件给人生节点留一个不会被冲走的存档事件发生的当下或几天内

1.3 完成条件（用户可见的「做完了」证据）

  • 任意一条记录提交后，立刻出现在首页手札流顶部；
  • 该记录在对应模块内可被检索、可被编辑、可被删除；
  • 倒计时类记录进入临期区间后，站内消息中心出现提醒；
  • 月底打开账本，能看到本月支出总额与分类构成，无需手工汇总。

1.4 共同对象：手札条目（Entry）

这是整个产品的支点。五个模块产出的东西长得完全不一样（一笔 -18.5 元的早餐、一次 7 天的川西行程、一个「距离发薪还有 3 天」的倒计时），但对用户来说它们是同一件事：「我的人生里又多了一条」。手札条目就是这条「一」，是首页时间线、全局搜索、数据导出三处功能的统一原料。

1.5 语气基线（写文案的规尺）

玩梗要玩在情绪位置（空状态、加载、成功、删除确认），不要玩在数据位置（金额、日期、资产净值必须精确直白）。

位置文案示例原则
手札流空状态「这里比你的钱包还干净。去记第一笔吧。」情绪位：可玩梗，但必须给出下一步动作，不做纯吐槽
账本空状态「你这个月还没花过钱 —— 除非你是在装。」
加载中「牛马拉磨中…」
记账成功「又活过一天 +1」
倒计时临近「距离发薪日还有 3 天，撑住。」情绪位：可玩梗，且要与数据一致
资产净值「家庭净资产 ¥1,286,400.00」——不加任何修饰数据位：零玩梗
删除确认「真的删？它可不会记仇。」情绪位：玩梗但必须把「可恢复」说清楚

2背景与目标 为什么要改造，以及改成什么样才算成

2.1 观察到的问题

一个人的生活数据天然是碎的：钱在记账 App、照片在相册、资产在 Excel、纪念日在手机日历、人生大事在朋友圈。用户不是不想记，是没有一个地方值得他记 —— 现有工具要么太专业（记账 App 的复式记账、券商 App 的持仓分析），要么太散（备忘录、相册）。

2.2 现有资产（改造的地基）

仓库里已经有一套完整但方向跑偏的骨架：三端脚手架已通、邮箱验证码与微信一键登录已完工、服务层数据隔离范式已成、运营后台 8 个页面已上、配置中心是元数据驱动的（加配置项不用建表）、定时任务与爬虫调度在跑、61 项后端测试全绿。

转向的判断：这套骨架的价值不在业务逻辑，而在「壳」。壳的价值远大于里面装的分红业务，所以改造方向是保留壳、换内核。

2.3 产品决策与期望的可见结果

由 2.1 与 2.2 推出：把「攒息」的专业外壳换成「人生手札」的随手容器，同时把已有的投资能力收编为资产模块的一个子能力，而不是丢掉。

期望的可观察结果（非量化指标，作为验收时的自我检查）：

  • 用户从打开 App 到完成一笔记账，操作不超过 3 次点击 + 1 次金额输入；
  • 首页首屏内能同时看到：本月支出、最近一条足迹、最近一个即将到来的日子；
  • 删除任何一条记录后，可在回收站找回，无需联系客服；
  • 新用户首次登录后，未填写任何数据时，五个模块的空状态都能告诉他「先做什么」。

3.1 最小完整闭环（P0）

入口条件：用户已登录（复用现有邮箱验证码 / 微信一键登录）。
P0 动作：创建一条任意模块的记录 → 记录进入手札流 → 可在模块内管理 → 倒计时类进入提醒通道 → 可删除并恢复。

3.2 P1 支持（本期不做，但结构上留位）

  • 账本：预算与超支预警、多币种记账、账单自动导入（支付宝/微信账单解析）；
  • 足迹：地图足迹热力图、按同行人/标签筛选、行程与账本自动互相关联；
  • 日子：农历节气的自动预置（春节/中秋）、与家庭成员共享同一批日子；
  • 家庭资产：资产自动估值刷新、资产负债的定期快照趋势图、投资收益率归因；
  • 通用：数据导出（JSON / CSV）、年度回顾报告（可分享图片）、PC 端补齐。

3.3 明确不做（避免范围蔓延）

排除项原因
好友 / 关注 / 动态流产品定位是「私人手札」，一旦引入社交，隐私边界、内容审核、举报处理都会变成新负担，且会稀释「随手记」的私密感。
AI 自动生成内容人生记录的价值在于「是我写的」。AI 代写会直接消解这个价值，且引入不必要的成本与合规问题。
与他人共享的家庭账本现有数据模型是严格的「一人一账号、各看各的」，改造为多人共享需要重做整个权限与可见性模型。这是本稿最大的待定项，见 §11。
第三方数据同步（银行/券商直连）合规与成本都远超收益；资产模块采用手工录入 + 现有爬虫辅助估值。
专业财务分析（复式记账/报表/税务）现有分红域已经够专业了，新品要往轻的方向走，不叠加专业负担。

4产品模型：统一记录 vs 独立模型 本稿最关键的一个取舍

4.1 两条极端路线的代价

路线它的样子为什么不能选
A. 完全统一模型
所有模块共用一张「记录表」+ 万能字段		 一条记录 = 标题 + 时间 + 若干自定义键值对。记账的金额、资产的市值、行程的目的地全塞进键值对里。 统计会变得不可做。账本的「本月餐饮支出合计」需要遍历所有记录并解析文本字段；资产的「净值趋势」需要跨表拼装。查询性能与代码可维护性双输，这是把关系型数据库当文档库用。
B. 完全独立模型
五个模块各管各的，互不相识		 每张表都是干净利落的强类型字段，各模块自己一套增删改查。 首页手札流要「按时间倒序，把五张表混在一起分页」。跨表排序 + 跨表分页是这个方案里最脏的部分，且每加一个模块就要改一次首页。全局搜索、数据导出同理。

4.2 本稿决策：混合模型

决策：各模块保留独立主表（保证统计能做），另加一个轻量「条目索引层」作为手札流与全局搜索的唯一数据源。

分工如下：

层存放什么服务于谁
模块主表
强类型		 该模块自己的完整字段。记账有金额/分类/账户；资产有市值/币种/负债；行程有目的地/起止日期/同行人。 模块内的统计、筛选、编辑、导出。这是各模块的唯一事实来源。
条目索引层
轻量		 只有公共属性：归属用户、条目类型（账本/旅游/大事件/日子/资产快照）、发生时间、标题、摘要、封面图、标签、关联主表记录号。 首页手札流的时间线、全局搜索、年度回顾、数据导出清单。是索引不是副本 —— 不回写、不做统计依据。

关键约束（防止索引层腐化）

  • 单向写入：只有「创建/编辑/删除模块记录」这一个动作会同步索引层，索引层永不反向修改主表；
  • 可重建：索引层任何时候都能由五张主表全量重建。因此它存的是「索引」而非「数据」，即使写坏也能修；
  • 不做统计：任何金额合计、趋势曲线都必须回主表算。索引层里的数字只用于展示，不参与计算；
  • 不计入回收站逻辑：回收站由主表控制，索引层随主表的软删除状态同步隐藏。

为什么这个设计能省事

它把「跨表 union 分页」这个最难的问题，转化成「单表单条件分页」这个最简单的问题。首页手札流只需要查索引层，不需要知道账本字段长什么样；而账本要算月支出时，也完全不需要管首页。

反过来说，代价是写入路径变长：每条记录创建时要多写一行索引。这在一个服务端串行处理的应用里成本极低，但必须保证「主表写入与索引写入在同一个事务里」—— 否则会出现手札流里有条目但点进去 404 的脏数据。这一条会写进 §7 共享规则。

5移动端信息架构 底部 5 个 tab，以及「家庭资产为什么不占 tab」

5.1 底部导航

位置tab承载什么
1🏠 手札首页时间线，聚合五模块条目 + 月度小结 + 置顶的临近日子。这是产品的门面。
2💰 账本记账流水、月视图、分类统计。使用频率最高的模块，给最好的位置。
3📸 足迹段内切换「旅游 / 大事件」。两者都是「翻回来看」的内容型模块，合并成一个 tab 更紧凑，也呼应现有移动端「相关模块合并进一个页面用 segment 切换」的既有设计约定。

家庭资产为什么不占 tab：它的使用频率是「季度级」，而五个 tab 是高频入口。低频功能占 tab 会浪费最贵的资源，也会让用户觉得「这个 App 还得管钱，很累」。因此它挂在「我的」下，同时在手札首页用一张小卡片做快捷入口 —— 入口存在感保留，但不必占用 tab。

M1 手札流（首页） P0

目的

让用户打开 App 的第一眼，就看到「我的人生最近发生了什么」。它不产生数据，只聚合数据，因此它的质量取决于其他模块，而不取决于自身。

布局（自上而下）

  1. 月度小结卡：本月支出总额 + 与上月对比；若本月有新增足迹或大事件，追加一行「本月你还去了 X、经历了 Y」。
  2. 置顶日子条：取用户置顶的倒计时中最临近的 1 条，以横向条呈现。没有置顶时，自动取最近的 1 条。
  3. 时间线：按发生时间倒序的条目卡片，每条只展示「封面图 + 类型徽章 + 标题 + 一行摘要」。
  4. 家庭资产快捷卡：若用户已建立资产数据，在时间线中每 10 条插一张轻量卡片，展示当前净值（低频入口的兜底存在感）。

触发

进入 tab 即加载；下拉刷新；从任意模块新增/编辑/删除记录后回到首页时需自动刷新（因为索引层已同步）。

处理规则

  • 时间线来源只有条目索引层（§4），不直接查各模块主表；
  • 分页：每页 20 条，滚动到底自动加载下一页；
  • 筛选：按类型（账本 / 足迹 / 日子 / 资产快照）分段筛选，默认「全部」；
  • 排序：固定按「发生时间」倒序。不支持按创建时间排序 —— 用户补记一笔上周的支出时，它应该出现在上周的位置，而不是今天的位置。

结果与状态变化

读取无副作用。但有两个例外需要明确：条目的可见性跟随其主记录的软删除状态（删除后立即从流中消失，恢复后回到原位）。

异常

场景表现
全空显示空状态 + 主行动按钮（「记第一笔」）。文案见 §1.5。
加载失败显示错误态 + 「再试一次」，不显示空白页。保留上一次成功数据（若有）。
分页到底显示「没有更早的了 · 你的人生还很长」，而不是空白。
索引层与主表不一致点进条目发现主记录不存在时，前端展示「这条记录已不存在」并静默移除该条目。这是索引层可重建（§4）必须配套的兜底。

M2 账本 P0

目的

用最低摩擦记下每一笔，并自动给出「钱花到哪了」。产品的日活主要靠它。

布局

顶部月度汇总卡（支出 / 收入 / 结余）→ 分类构成条 → 当日流水列表（按日分组）。快速记一笔为全屏弹层，不跳页面。

快速记一笔的处理规则（核心）

  • 进入弹层后金额输入框默认聚焦，直接弹数字键盘，用户不需要先点一下；
  • 金额键盘上方固定一个「支出 / 收入」切换，默认支出；
  • 分类以横向 chips 呈现，默认选中上一次使用的分类（而非「餐饮」）—— 连续记账场景下这能省掉一次点击；
  • 日期默认今天，可回溯，不可选未来日期；
  • 备注、照片、账户三个字段折叠在「更多」里，默认不展开，保证主路径只有「金额 → 分类 → 保存」三步。

字段

字段必填规则
金额是大于 0，最多 2 位小数，上限 9,999,999.99。为 0 或空时不允许保存。
收支类型是支出 / 收入，默认支出。
分类是预置：餐饮 / 交通 / 居住 / 购物 / 人情 / 娱乐 / 医疗 / 学习 / 其他。可自定义，自定义分类最多 20 个。
日期是默认今天；可选过去任意日期；不可选未来。
账户否现金 / 微信 / 支付宝 / 银行卡 / 其他。
备注否最多 50 字。
照片否最多 1 张（小票），规则见 §7.3。

状态

账目只有两个状态：已记录 与 已删除（回收站）。不做草稿态 —— 记账这件事没有「写一半」的合理场景，草稿会制造「我到底记了没有」的焦虑。

异常

  • 重复提交：保存按钮点击后立即置为不可用，直到请求返回；
  • 保存失败：弹层不关闭，输入内容保留，顶部提示失败原因并允许重试；
  • 分类为空的自定义分类：删除分类时，已归属该分类的账目自动落入「其他」，不阻断删除。

M3 足迹 · 旅游 P0

目的

让照片从「相册里再也不打开的第 8,000 张」变成「一个可以被翻回去的行程」。这是全产品情绪价值最高的模块。

布局

列表页为卡片流（封面图占卡片上半部）；详情页为「封面大图 → 基本信息 → 照片瀑布 → 正文 → 花费」。列表顶部有一行统计：「去过 7 座城市 · 3 趟行程」。

处理规则

  • 创建行程时，目的地（城市）为必填，起止日期必填；标题可由「城市 + 日期」自动生成，允许用户改写；
  • 行程进行中可随时追加照片，此时行程状态为进行中，在列表里排在最前并带一个「进行中」标记；
  • 行程结束后可补写正文与花费，状态转为已结束；
  • 「去过 N 座城市」按去重后的城市数统计，同城多次行程只计一次。

字段

字段必填规则
标题否默认「城市 + 起止月日」，最多 30 字。
目的地是多选城市，最多 5 个，可输入自定义。
起止日期是同日行程允许（当日往返）；结束日期不早于开始日期。
同行人否自由文本，最多 30 字。本期不做联系人体系，避免引入用户间关系。
封面图否未设时，自动取照片集中的第一张；无照片时使用按城市名生成的纯色占位卡。
照片集否最多 20 张，规则见 §7.3。
正文否最多 1000 字。
花费否手工填写；也可关联账本中该时间段内的「旅游」分类合计（P1）。

异常

  • 照片上传中关闭页面：已上传成功的照片保留，未完成的丢弃，行程本身仍可保存（照片是可选增强，不应阻断主流程）；
  • 单次上传超过上限：超出部分被拒绝并提示「最多 20 张，已保留前 20 张」；
  • 行程被删除：照片一并进入回收站，30 天内可随行程恢复。

M4 足迹 · 人生大事件 P0

目的

给人生节点一个不会被平台冲走的存档。与旅游的区别在于：旅游是「一段时间」，大事件是「一个时刻」。

布局

按年份分组的时间线（2026 / 2025 / 2024…），每组右侧显示当年事件数。事件卡为横向三行：emoji 图标 + 标题 + 日期与类型。

处理规则

  • 事件日期允许选未来（例如「下个月入职新公司」），未来事件的卡片以虚线框区分；
  • 类型预置：工作 / 学业 / 家庭 / 健康 / 财务 / 里程碑 / 自定义，自定义类型自带一个 emoji 选择；
  • 心情 emoji 为可选字段，用于列表页的视觉点缀，不参与任何统计；
  • 默认单条事件不可设为公开 —— 本产品无公开概念，全部内容仅本人可见（见 §7.4）。

字段

字段必填规则
标题是最多 30 字。
日期是可未来。
类型是预置 6 类 + 自定义；自定义需选 emoji。
正文否最多 2000 字。
照片否最多 9 张。
心情否单个 emoji。
标签否最多 5 个，用于全局搜索。

M5 日子（重要日子倒计时） P0

目的

让用户「不忘记」，并「提前有准备」。这是全产品技术链路最短、却覆盖了全部基建（创建 → 状态 → 提醒 → 手札流 → 删除）的模块，因此被选为第一个交付批次。

布局

两个 segment：倒计时列表 / 月历。列表顶部为「最临近的日子」大卡（环形进度），下方为普通列表项；月历页点日期查看当天日子。

重复规则

规则行为
一次性日期过后进入「已过去」，排序沉底，保留在列表供回看。
每年（公历）日期过后自动滚动到下一年的同月同日，卡片显示「第 N 年」。
每月日期过后自动滚动到下一月同日；当目标日为 29/30/31 而该月无此日时，取该月最后一天。
每年（农历）按农历日期换算为当年的公历日期。农历换算在本地完成，不依赖网络。
农历是需要单独说明的一条：它影响倒计时的天数计算与提醒触发。若本地换算出错，用户会错过生日这类最重要的日子。因此农历换算必须与公历日期同时展示（卡片上同时显示「农历九月十六」和换算后的公历日期），让用户能一眼核对。

提醒档位

可多选：提前 30 天 / 提前 7 天 / 提前 1 天 / 当天。默认勾选「提前 7 天」与「当天」。提醒的送达方式见 §7.2。

状态与视觉

状态判定列表表现
普通剩余 > 30 天常规列表项，数字为剩余天数。
临近剩余 8–30 天数字用品牌色，不加额外装饰。
紧迫剩余 1–7 天卡片底色转为浅暖色，文案带情绪（见 §1.5）。
就是今天剩余 0 天置顶显示，全站最高视觉优先级。
已过去已过且为一次性灰显并沉底，显示「已过去 N 天」。

置顶

最多置顶 3 个。置顶的日子优先出现在列表顶部与首页置顶条；置顶位已满时提示「最多置顶 3 个，先取消一个吧」。

字段

字段必填规则
名称是最多 20 字。
日期是一次性可任意日期；重复规则下只需填首个日期。
重复规则是一次性 / 每年 / 每月 / 每年农历，默认一次性。
提醒档位否多选，默认「提前 7 天 + 当天」。
配色 / emoji否用于列表辨识。
备注否最多 100 字。

M6 家庭资产 P0 含收编

目的

回答「我家到底有多少钱」。它是低频模块，但提供了全产品最重的数据价值，也是现有投资域唯一的合法去处。

布局

顶层为净值卡（净资产 + 环比变化）→ 资产分类清单（可分项展开）→ 负债清单 → 快照趋势。

分类与规则

分类录入方式
现金与存款手工填写总额（活期 / 定期分项可选）。
投资持仓收编由原「攒息」的持仓与批次自动汇总，市值按最新可得数据估值；失败时保留上一次成功估值并标注「估值时间」。
房产 / 车辆手工填写估值，可标注「自住 / 投资」。
其他资产自定义名称 + 金额。
负债房贷 / 车贷 / 消费贷 / 其他，手工填写余额，可记录还款日（还款日可一键生成一个「日子」条目）。
  • 净资产 = 资产合计 − 负债合计，多币种资产按当日汇率折算为人民币后合并；
  • 快照：用户每次「盘点」生成一份带日期的快照，用于趋势图。系统不自动生成快照 —— 自动快照会让曲线被无意义的波动（当日行情）污染；
  • 投资持仓的明细（持仓 / 批次 / 分红记录 / 分红日历 / 预案）位于三级页面，复用现有能力，入口在「投资持仓」项上。

与投资域调性的隔离

家庭资产整块不使用玩梗文案。进入这一层后，界面回到克制的专业风格（沿用现有蓝色系与现有卡片结构）。这是 §0 决策「分模块调节语气」的具体落点 —— 同一个 App 里允许两种语气，靠模块边界切换。

异常

  • 估值为空（新用户尚未录入持仓）：投资项显示「暂未录入，去添加」，不显示 0；
  • 汇率缺失：使用兜底汇率并在净值卡上标注「按兜底汇率折算」；
  • 负债为 0：显示「无负债」而非留空。

内容

分组项

M8 媒体中心 新增 P0

目的

照片是本产品从「表单」变成「手札」的关键。没有照片，旅游和大事件两个模块几乎不成立。

规则

  • 上传即压缩：上传前在客户端压缩到最长边 1920px，超过则按质量递减压缩，保证单张一般不超过 1MB；
  • 硬上限：单张原图不超过 10MB，超出拒绝并提示；
  • 数量上限：账目 1 张 / 事件 9 张 / 行程 20 张（按模块配置化，见 §7.5）；
  • 格式：仅接受 jpg / jpeg / png / webp / heic；
  • 可见性：所有照片仅本人可访问，不允许通过公开链接直接访问，访问需带身份校验；
  • 删除联动：删除所属条目时照片一并进入回收站；回收站到期清理时才真正删除文件。

「先存照片，稍后归类」

这是降低录入摩擦的核心设计。快捷新增里有第六个入口「只传照片」：用户可以先批量把照片扔进来（例如行程中随手拍），系统把它们存为「未归类的照片」，之后在手札流里慢慢归类到行程或事件。如果没有这个入口，用户在路上就不会打开 App，因为他们没时间想「这属于哪次行程」。

异常

  • 上传中断：已成功的保留，失败的可单张重试；
  • 上传失败但用户已保存条目：条目不回滚，照片位显示「图片加载失败」占位，可重新上传；
  • 照片被判为不支持格式：拒绝并列出文件名，允许用户跳过继续。

M9 提醒与通知中心 新增 P0

目的

让倒计时真正有用。同时诚实地收窄承诺 —— 移动端的推送能力有硬限制，产品文案不能承诺「微信必达」。

通道与能力边界

通道可靠性说明

9分期路线 五批交付，每批都可用、可回退

批次交付内容为什么这样排
S0
地基		 媒体上传与存储 · 条目索引层 · 统一软删除与回收站 · 品牌改名与 IA 换血（5 tab） · 「我的」页改版 这四件事是后面所有模块的公共依赖，返工代价最高。此批结束后界面看起来仍是"空壳"，但这是必要的。
S1
先跑通链路		 日子模块 + 提醒与消息中心（先只做站内消息 + 邮件） 选它当头阵，是因为它技术链路最短，却覆盖了全部基建：创建 → 状态计算 → 提醒触发 → 手札流展示 → 删除与恢复。用它把 S0 的三块地基真正跑通验证一遍，风险最低。
同时它不依赖照片，可以验证「无照片模块」的排版是否也立得住。
S2
主模块		 账本模块 + 手札流月度小结卡 使用频率最高、最能带来日活的模块，放在链路已验证之后做。
S3
收编		 家庭资产模块 + 原投资域整体下沉为「资产 · 投资」子页 此批是纯改造（不新建大功能），适合放在连续两个新建模块之间做缓冲，同时它让原「攒息」内容在新产品里正式落位，为下批腾出干净的五 tab 结构。
S4
内容模块		 足迹模块：旅游 + 大事件 + 小程序订阅消息接入 + 数据导出 两个重照片模块同批做，共用同一套媒体展示组件，一起验证 S0 的照片地基在大规模场景下是否成立。订阅消息放在这批接入，因为它是唯一需要用户逐次授权的通道，先让产品跑起来看真实授权率。
S5
打磨		 P1 项按需挑选（年度回顾、导出分享、预算、地图足迹）· PC 端去留决策 此时产品已有真实用户与真实数据，P1 的优先级应该由数据决定，而不是由设计稿决定。
每批的验收方式：每批上线后，用模块灰度开关控制可见范围；若某批上线后出现严重问题，关闭该模块开关即可回退，已产生的数据保留。这是「五模块全部纳入 MVP」这个激进目标之下唯一的安全绳。

10风险与对策

风险级别说明与对策
媒体存储成本与体积失控 高 照片是唯一的成本增长点，且用户不会自己节制。
对策：上传前强制压缩（最长边 1920px）；单条目数量硬上限；回收站照片随条目才真正删除；后台提供占用空间统计与单张上限配置项，必要时可动态收紧。
提醒不可靠导致的信任损伤 高 H5 无推送、小程序订阅消息一次性授权，用户很可能「没收到提醒」并认为产品坏了。
对策：①站内消息作为必备可靠通道；②设置页明确写出限制（§6 M9 的硬性文案规则）；③不承诺「准时送达」；④提供邮件通道作为用户可选的长效兜底。
五模块同时纳入 MVP 导致失焦 高 把五个模块全塞进 MVP 是范围风险，容易做成「五个都半成品」。
对策：已按 §9 拆成五批，每批独立可用可回退；S1 用最短链路验证地基，把风险压在最前面。
调性冲突：玩梗产品装严肃金融数据 中 同一 App 里既有「牛马拉磨中…」又有「家庭净资产 ¥1,286,400.00」，可能显得割裂。
对策：§6 M6 约定按模块边界切换语气 —— 资产模块内零玩梗，回到克制专业风；其余模块玩梗。靠边界而非靠全局统一。
索引层与主表数据不一致 中 §4 的单向同步一旦不在同一事务里，会出现「手札流有条目、点进去 404」。
对策：索引写入与主记录写入强制同事务；索引层随时可全量重建；前端对「主记录不存在」的条目做静默移除兜底（§6 M1）。
品牌改名对既有用户的冲击 中 「攒息」已有一批演示/真实用户，改名后他们可能找不到原有功能。
对策：①原投资功能不删，只是入口下沉，且保留 PC 端独立入口；②首次进入时在「家庭资产」给出一次性引导说明功能去哪了；③是否保留「攒息」作为投资子品牌为待定项（§11）。
注销数据丢失的分量变大 中 注销原来删的是分红记录，现在删的是几年人生记录与照片。
对策：§6 M7 规定注销确认页必须显式列出将被删除的条目与照片数量，并要求二次确认。这是本稿唯一一处「必须加重的确认」。
管理员可见范围扩大带来的隐私风险 中 用户数据从金额变成照片与私人文字。
对策：§7.4 的新红线 —— 后台不可查看用户照片原件，只可见数量与占用；单用户排查页不提供照片预览。
「家庭共享」需求会冲击现有模型 待定 「家庭资产」这个词天然暗示多人共享，但现有模型是严格一人一账号。
对策：MVP 期内明确不做共享（§3.3），并在文案上避免「全家一起记」这类暗示。是否要做留待 §11 决策。
已存在的社区模块与私人定位冲突 低 仓库里已有一个社区相关接口，而本产品定位是「私人手札、不做社交」。
对策：建议本期下线或暂不接入（§11 待定）。留着不管会与定位打架，还会给用户造成预期错位。

11待定问题 需要你拍板的、会实质改变设计的决策

问题影响面为什么必须先定
要不要做「家庭共享」？ 极大 「家庭资产」「家庭账本」这两个词都暗示多人。若要做，整个权限与可见性模型要从「一人一账号」改成「一个空间多成员」，§7.4 的权限矩阵、条目索引层的归属字段、回收站归属都要重做，等于把 S0 地基重新设计一次。若不做，则需在文案上彻底避免「全家一起记」的暗示。
MVP 的五批顺序是否照 §9 走？ 大 §9 建议首批做「日子」，理由是它链路最短但覆盖全部基建，能用最低成本验证 S0 的三块地基。若你更希望先看到「账本」的效果，顺序可以互换 —— 但媒体地基必须排在含照片的模块（旅游 / 大事件）之前，这一条不能调。另外「分五批」本身是可以砍的，代价是每批的返工风险上升。
「攒息」是否保留为投资子品牌？ 中 若保留：家庭资产 · 投资页沿用「攒息」这个名字与蓝色视觉，老用户有连续性，§6 M6 的「模块内换语气」也更有解释力。
若不保留：品牌彻底统一为「纯牛马人生手札」，但需要处理老用户的「我的持仓去哪了」的迁移认知，且要一次性做完全站视觉替换。
PC 端最终去留 中 本稿默认「PC 只保留运营后台、面向用户页面暂停维护但不删除」。若后续要补 PC 端，每个移动模块都要额外补一页，工作量基本翻倍。建议等 S2 结束后，用真实用户设备分布再决定，而不是现在拍。
仓库里已存在的社区接口怎么处理？ 中 它与「私人手札、不做社交」的定位直接冲突（§3.3）。选项只有两个：下线（推荐，代价最小，但需确认无用户数据依赖），或改造为匿名树洞（但这等于部分反悔「不做社交」的决策，会带来内容审核与举报处理的长期负担）。
是否接入小程序订阅消息 中 接入需要用户逐次授权，真实授权率可能很低，投入产出不一定划算。若不接入，微信内的倒计时提醒就只能靠站内消息 —— 意味着用户必须主动打开小程序才能看到提醒，倒计时的价值会大幅缩水。这是「提醒模块」最需要先验证的一个假设。
现有演示/老用户数据如何迁移 中 现有库里的持仓与分红数据在新 IA 下需要归位到「我的 → 家庭资产 → 投资持仓」。需要确定：①是直接沿用现有数据（老用户开箱即用，但他们会看到一堆陌生模块），②还是新建一套五模块演示数据用于评审（看点更全，但会与真实数据混在一起）。
数据导出格式 低 JSON（完整字段，便于日后迁移）/ CSV（账本流水，便于 Excel 分析）/ 照片压缩包。三者是否都要做，还是先只做 JSON。影响很小，可延到 S4 再定。
